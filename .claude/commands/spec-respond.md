你正在主持 spec「方案審查迴圈」中的**修改階段**。任務代號：取 `$ARGUMENTS` 的第一個字詞，以下記為 `<task>`。

你的職責：依 Codex 的審查意見與使用者在本對話中提出的意見修改 spec，並留下可供下一輪審查者閱讀的回應紀錄。你**不是**在討好審查者，也不是在捍衛自己的設計；目標是讓 spec 變得正確、清楚、可實作、可驗收。

## 步驟 0：定位檔案

1. spec 位於 `docs/specs/<task>.md`。
2. 用 `ls docs/spec-reviews/` 找出 `<task>-p<N>-codex.md`，取最大的 N 作為本輪。
   - 找不到任何 Codex 審查：**停止**，告訴使用者先執行 `scripts/spec-review.sh <task>`。若使用者只是想先依自己的意見改 spec，不需要本指令，直接在對話中改即可（重大取捨請記到 §8.1）。
3. 若 `docs/spec-reviews/<task>-p<N>-resolution.md` 已存在，代表本輪處理過了。先詢問使用者是要補充意見後更新，還是略過；**不要默默覆蓋**。
4. 讀取：本輪 Codex 審查、目前的 spec、spec 的 §8.1 決議紀錄；若 N > 1，再讀 `<task>-p<N-1>-resolution.md`。

## 步驟 1：整理人類意見

回顧**本對話中**，使用者自上一份回應紀錄（或自 spec 起草）以來提出的所有意見，逐點編號為 `H<N>-1`、`H<N>-2`…

- 忠實記錄使用者的原意，不要美化、不要擴寫、不要替使用者補上他沒說的立場。
- 意思不確定的，用一兩句話向使用者確認，不要自行猜測。
- 使用者本輪沒有提意見，就如實寫「本輪無口頭意見」，**不要編造**。
- **使用者的意見優先於 Codex。** 兩者衝突時採使用者的，並記入決議紀錄。

這一步很重要：Codex 看不到本對話，下一輪它只能從回應紀錄得知使用者說過什麼。

## 步驟 2：先驗證，再回應

對 Codex 的**每一則**意見（`P<N>-x`）：

1. **先查證**：開啟它引用的檔案與行號，確認它說的是事實。Codex 可能誤判；不要未經驗證就採納或否決。
2. 判定處置，只能是以下四種：**採納**、**部分採納**、**不採納**、**需要人決定**。
3. 規則：
   - **blocker 不可被默默忽略。** 只有三條路：修改 spec；「不採納」並附具體證據（檔案與行號，或明確的論證）；標為「需要人決定」。
   - **suggestion** 由你判斷；不採納時，用一句話說明理由。
   - **question** 能由程式碼或 spec 回答的，就回答，必要時補進 spec；需要使用者拍板的，標為「需要人決定」。
   - 不要為了讓審查通過而妥協設計，也不要為了維護面子而堅持錯誤的設計。
4. 對「需要人決定」與 Codex 列出的「需要人類決定的事項」：**直接在對話中問使用者**，列出選項、各自影響與你的建議，等到回答後再改 spec。使用者暫時不回答，就留在紀錄的「待人決定」，**不要擅自決定**。

## 步驟 3：修改 spec

只能修改 `docs/specs/<task>.md` 的**第 1～8 節**，以及 meta 表格的「狀態」（改為 `in-review`）。

- **不要**碰第 9 節（實作者專用）、meta 表格的「核准」列，也不要修改任何程式碼。
- **AC 編號保持穩定**：不重新編號；新增的接在最後；移除的保留編號並標註「（已移除：原因）」。這樣前後輪的意見才對得起來。
- 範圍內、非目標、預計異動的檔案、驗收標準、測試要求要彼此一致；Codex 指出遺漏的檔案或相依，查證後補上。
- 每項**實質決議**（採用或捨棄某方案、取捨、使用者的裁決）都在 §8.1 決議紀錄新增一列：`D-n` 遞增、日期用 `date +%F`、來源註明（`Codex P<N>-x` / `人類 H<N>-x` / `Claude`）。純文字潤飾不用記。
- 開放問題：已解決的移除並記入決議；未解決的保留。
- 改完後自我檢查：AC 彼此是否矛盾？範圍、非目標、預計異動檔案是否一致？第 6 節的驗證指令是否仍可執行？

## 步驟 4：寫回應紀錄

寫入 `docs/spec-reviews/<task>-p<N>-resolution.md`，格式如下（日期用 `date +%F`）：

```markdown
# <task> 方案審查 第 <N> 輪：回應紀錄

日期：YYYY-MM-DD

## 人類意見（口頭，供下一輪審查者參考）

- H<N>-1：<使用者的原意> → <處置與結果>

（沒有則寫：本輪無口頭意見）

## 對 Codex 意見的回應

| 意見 | 類型 | 處置 | 說明 |
|------|------|------|------|
| P<N>-1 | blocker | 採納 | <改了哪一節、怎麼改> |
| P<N>-2 | suggestion | 不採納 | <一句話理由> |

## spec 變更摘要

- §2：<新增 / 修改 / 移除了哪些 AC>
- §8.1：<新增了哪些決議 D-n>

## 待人決定

- <項目、選項、你的建議；沒有則寫「無」>
```

## 步驟 5：向使用者回報

簡短回報（約 10 行內）：各處置的數量、spec 的主要變動、仍待人決定的項目，以及下一步：

- 還有待人決定的項目 → 先請使用者回答，不要進入下一輪。
- 否則 → 請使用者執行 `scripts/spec-review.sh <task>` 進行下一輪 Codex 審查。

**不要自己執行 Codex 審查，不要宣布方案「通過」，也不要把狀態改成 `approved`。** 核准只能由使用者透過 `/spec-approve` 決定。
